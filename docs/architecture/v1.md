# MesoForge v1 Architecture and Implementation Plan

> **For Hermes:** Use subagent-driven development to implement this plan phase-by-phase, with architecture review at each phase boundary.

**Goal:** Define a reproducible, scientifically defensible v1 platform that ingests numerical guidance, produces a deterministic baseline, constrains AI recommendations, and verifies every forecast layer.

**Architecture:** Build a Python-first modular monolith whose scientific functions operate on versioned xarray contracts while control-plane records and immutable artifact manifests preserve state and lineage. Keep deterministic forecasting and policy enforcement independent of AI, with explicit artifact seams for future distributed workers.

**Tech stack:** Python, Herbie/cfgrib, xarray, NumPy, Pint/pint-xarray, Pydantic, PostgreSQL, S3-compatible object storage, Parquet/DuckDB, FastAPI, and a workflow orchestrator selected by spike.

---

**Status:** Initial proposal  
**Audience:** Engineering, meteorology, data science, operations  
**Architecture stage:** Greenfield  
**Recommended approach:** Python-first modular monolith with explicit scale-out seams

## 1. Executive summary

MesoForge should begin as a Python modular monolith organized around a reproducible forecast pipeline:

```text
Guidance acquisition
    → canonical normalization
    → temporal/spatial alignment
    → source/aligned meteorological diagnostics
    → deterministic uncorrected blend
    → deterministic bias correction and final baseline
    → baseline-derived diagnostics
    → bounded AI recommendations
    → policy validation and approval
    → forecast publication
    → observation matching
    → verification and backtesting
    → leakage-safe bias learning
```

The central architectural principle is that every forecast must be reconstructable. Each published value should be traceable to:

- Source model cycles and files
- Retrieval and decoding versions
- Spatial and temporal transformations
- Baseline algorithm and configuration
- Diagnostics
- Bias estimates
- AI recommendations and supporting evidence
- Deterministic safety-policy decisions
- Human actions, when applicable
- Final forecast version

MesoForge should not begin as a collection of microservices. A modular monolith provides lower operational overhead, easier scientific iteration, and stronger transactional consistency while the domain and forecast methods are still evolving. Modules should nevertheless communicate through versioned contracts and artifact references so that expensive or independently scalable workloads can later move to separate workers or services.

## 2. Goals

MesoForge should support:

1. Ingestion of HRRR, NBM, RRFS, GFS, and ensemble guidance using Herbie, xarray, and related scientific Python tools.
2. Canonical representation of heterogeneous guidance without erasing source-specific meaning.
3. Explicit temporal and spatial alignment.
4. A deterministic, auditable baseline forecast.
5. Meteorological diagnostics derived from source and aligned fields.
6. AI-recommended adjustments to temperature, wind, probability of precipitation, and quantitative precipitation forecast.
7. Hard, deterministic limits around AI influence.
8. Forecast verification against observations.
9. Reproducible retrospective backtesting.
10. Local and model-specific bias learning without future-information leakage.
11. Programmatic APIs and a meteorologist-facing UI.
12. A credible path from one-machine development to distributed production processing.

## 3. Non-goals for the initial architecture

The first releases should not attempt to provide:

- A general-purpose atmospheric modeling framework
- Training or running full numerical weather prediction models
- Unrestricted AI generation of forecast grids
- Fully autonomous forecast publication
- A microservice per domain concept
- A bespoke workflow engine, array format, or geospatial database
- Immediate nationwide, all-model, all-variable, high-resolution retention
- Online learning from observations as soon as they arrive
- Bitwise reproducibility across arbitrary hardware and dependency versions

The initial objective is a trustworthy end-to-end forecasting and verification loop for a bounded geography, variable set, and forecast horizon.

## 4. Architectural principles

### 4.1 Forecast artifacts are first-class records

A forecast is not merely the latest array in storage. It is an immutable, versioned artifact with lineage. Corrections create new versions; they do not overwrite history.

### 4.2 Scientific computation is separated from orchestration

Meteorological algorithms should be pure or nearly pure functions over typed datasets and configuration. Workflow code schedules those functions, records their execution, and manages retries.

### 4.3 Preserve source semantics before normalizing

Model-specific variables, accumulation conventions, vertical coordinates, grids, and missing-value behavior must remain available. Canonicalization should add a consistent interpretation while preserving the original metadata and raw source artifacts.

### 4.4 Time and space are explicit types, not conventions

Forecast reference time, valid time, lead time, interval bounds, accumulation windows, grid definitions, and station locations must be represented explicitly in contracts.

### 4.5 Deterministic logic owns the forecast

AI may recommend adjustments and explain them. Deterministic code calculates the baseline, enforces bounds, validates physical and cross-variable consistency, and decides whether an adjustment is eligible for publication.

### 4.6 Reproducibility precedes sophistication

Every algorithm, model, prompt, policy, dependency environment, and configuration used by a run must have a stable identity.

### 4.7 Training and evaluation follow event-time semantics

Bias models may use only information that would have been available at the historical forecast issuance cutoff. Later revisions and delayed observations cannot silently leak into training features.

### 4.8 Start local; preserve scale-out seams

Use in-process module calls and background workers initially. Place explicit artifact and task boundaries around acquisition, regridding, diagnostics, verification, and model training so those workloads can later be distributed.

## 6. Domain boundaries

The modular monolith should enforce the following package boundaries.

### 6.1 Catalog and configuration

Owns:

- Model, product, variable, domain, grid, station, and provider definitions
- Canonical variable registry
- Units and vertical-level definitions
- Runtime configuration resolution
- Configuration versioning and validation

It must not contain retrieval or forecast-generation logic.

### 6.2 Guidance acquisition

Owns:

- Herbie-based discovery and retrieval
- Provider availability checks
- Checksums and source metadata
- Raw-file registration
- Retry, partial-availability, and late-arrival behavior
- Idempotent acquisition manifests

Output: immutable raw-source references and source inventories.

The acquisition manifest is the reproducibility boundary for Herbie and GRIB decoding. In addition to a file checksum it must retain the Herbie template, product, cycle, forecast hour, provider and resolved source URL; the Herbie version; the inventory/index artifact; every GRIB search expression; the selected message numbers and identifying GRIB keys; and the `cfgrib`/backend arguments used to open each hypercube. Ambiguous or duplicate matches fail normalization rather than silently selecting the first message. When a logical variable requires multiple files or hypercubes, its lineage maps each variable/lead/member slice to the exact selected messages.

### 6.3 Decode and normalization

Owns:

- GRIB decoding through xarray-compatible adapters
- Unit conversion
- Coordinate normalization
- Canonical variable naming
- Source-specific interpretation
- Missing-data and quality flags
- Conversion to analysis-ready array artifacts

Output: canonical guidance datasets that retain source metadata.

### 6.4 Spatial and temporal alignment

Owns:

- Regridding
- Point extraction
- Vertical interpolation where authorized
- Lead-time alignment
- Accumulation-window conversion
- Interpolation policy
- Coverage masks
- Alignment reports

This domain must distinguish “not available,” “outside coverage,” and “calculated but invalid.”

### 6.5 Deterministic forecast baseline

Owns:

- Model eligibility
- Blend weights
- Conditional and lead-dependent blending
- Deterministic local corrections
- Missing-model fallback behavior
- Baseline forecast production

It must never invoke a language model or depend on nondeterministic output.

### 6.6 Meteorological diagnostics

Owns derived quantities such as:

- Temperature and dew-point relationships
- Wind speed, direction, and vector components
- Thermal advection or gradients where supported
- Precipitation timing and accumulation summaries
- Ensemble spread and exceedance probabilities
- Model disagreement
- Run-to-run trends
- Convective or stability indices when required data are available

Each diagnostic declares its required inputs, units, grid assumptions, vertical coordinates, and validity conditions.

Every diagnostic also declares one execution stage: `source_native`, `aligned_comparative`, or `baseline_derived`. Source-native diagnostics cannot compare models; aligned-comparative diagnostics require a common grid, valid-time/interval definition, and vertical definition; baseline-derived diagnostics consume the immutable final baseline. Stage and input artifact IDs are part of the diagnostic identity, preventing accidental comparison across incompatible grids, cycles, or levels.

### 6.7 Bias intelligence

Owns:

- Historical feature construction
- Bias estimators and statistical models
- Training snapshots
- Feature and target cutoffs
- Model registry metadata
- Bias prediction
- Drift and applicability checks

Bias output is evidence supplied to the baseline or adjustment process, not an uncontrolled override.

### 6.8 AI recommendation

Owns:

- Construction of bounded, structured AI inputs
- Prompt and model versioning
- Structured-output validation
- Recommendation rationales
- Evidence references
- Confidence and abstention
- AI call metadata

It produces proposals only.

### 6.9 Adjustment policy and approval

Owns:

- Allowed variables and horizons
- Absolute and rate-of-change limits
- Spatial and temporal smoothness checks
- Cross-variable consistency
- Confidence and evidence requirements
- Automatic accept, review, or reject decisions
- Human approval records
- Kill switches and fallback behavior

Only this module may turn an AI proposal into an accepted adjustment.

### 6.10 Forecast publication

Owns:

- Forecast version assembly
- Publication state transitions
- Product generation
- Supersession and correction semantics
- Downstream delivery manifests

### 6.11 Observations and verification

Owns:

- Observation ingestion and quality control
- Station and grid metadata
- Revision-aware observation records
- Forecast-to-observation matching
- Metrics, stratification, and aggregations
- Verification reports

### 6.12 Backtesting and experiments

Owns:

- Historical replay
- As-of data selection
- Comparable experiment definitions
- Baseline/challenger evaluation
- Statistical confidence calculations
- Promotion evidence

It should call production forecast functions rather than duplicate them.

### 6.13 Application interfaces

Owns:

- HTTP/API contracts
- Authentication and authorization
- UI-specific read models
- Review workflows
- Export adapters

It should not contain meteorological algorithms.

## 7. Core data contracts

Use xarray datasets for multidimensional scientific data, Pydantic models for control-plane records, and Arrow/Parquet for tabular observations and verification results. Units should be normalized with a controlled registry, preferably backed by Pint/pint-xarray.

### 7.1 Artifact identity

Every durable artifact should have a manifest similar to:

```yaml
artifact_id: content-addressed-or-generated-id
artifact_type: canonical_guidance
schema_version: guidance.v1
created_at: UTC timestamp
run_id: forecast-run-id
parents: [raw-artifact-id]
code_revision: git-commit
environment_digest: locked-environment-or-image-digest
configuration_digest: hash
storage_uri: object-store-uri
content_checksum: sha256
```

Large arrays stay in object storage; metadata stores contain references, never serialized arrays.

### 7.2 Canonical guidance dataset

```yaml
required_dimensions: [lead_time]
optional_dimensions: [member, level, y, x, location]
support_dimensions: [bounds=2]
coordinates:
  forecast_reference_time: scalar datetime64[ns], UTC with no timezone object
  lead_time(lead_time): timedelta64[ns]
  valid_time(lead_time): datetime64[ns], derived and validated
  member(member): optional source member identifier
  level(level): optional canonical vertical coordinate
  y(y): optional projected northing/index
  x(x): optional projected easting/index
  latitude(y,x): optional degrees_north
  longitude(y,x): optional degrees_east
  location(location): optional station/point identifier
data_variables:
  air_temperature_2m:
    dimensions: [lead_time, y, x]
    units: K
    temporal_semantics: instantaneous
    level_type: height_above_ground
    level: 2 m
  precipitation_amount:
    dimensions: [lead_time, y, x]
    units: kg m-2
    temporal_semantics: accumulation
    interval_bounds: precipitation_amount_interval_bounds
  precipitation_amount_interval_bounds:
    dimensions: [lead_time, bounds]
    encoding: datetime64[ns]
attributes:
  time_encoding: UTC
  grid_id: canonical-grid-definition-id
  variable_lineage_manifest_id: per-variable-and-slice source mapping
  normalization_version: normalize.v1
```

One artifact represents one reference cycle and one compatible grid, vertical topology, and lead axis. Permitted variable dimension tuples are explicit contract variants: point fields use `(lead_time, location)`; deterministic grids use `(lead_time, y, x)`; ensembles prepend `member`; vertical fields insert `level` before spatial dimensions. A validator rejects undeclared dimension orderings. Ragged lead availability is represented by explicit availability/quality masks or separate artifacts, not padded without provenance.

Each interval-valued variable references its own `(lead_time, bounds)` bounds variable and declares interval closure plus accumulation/probability semantics; bounds are not dataset-wide coordinates. Variables may share an artifact only when their lead axis and spatial/vertical topology are compatible, while differing variable-specific windows remain representable through separate bounds variables. UTC is encoded as timezone-naive `datetime64[ns]` plus the mandatory `time_encoding: UTC` attribute because NumPy/xarray do not reliably preserve timezone-aware datetime coordinates.

Dataset-level attributes describe only properties shared by every variable. Source model, product, file, hypercube, GRIB message, and transformation lineage live in the referenced lineage manifest, addressable per variable and, when needed, per lead/member. A standardized dataset must never imply a single source when it was assembled from multiple products or artifacts.

### 7.3 Forecast value contract

A logical forecast value should be identifiable by:

```text
forecast_version
location_or_grid_cell
variable
vertical_definition
forecast_reference_time
valid_time
interval_start
interval_end
value
unit
quality_flags
provenance_reference
```

### 7.4 Adjustment proposal bundle

```yaml
proposal_bundle_id: UUID
baseline_forecast_id: immutable reference
adjustments:
  - variable: temperature_2m | dew_point_2m | wind | wind_gust | pop | qpf | precipitation_type
    scope:
      geometry_id: domain or zone
      valid_start: UTC instant
      valid_end: UTC instant
    operation: additive | multiplicative
    magnitude: numeric or compact field reference
    unit: canonical unit
confidence: 0..1
rationale: short text
evidence_artifact_ids: [...]
ai_provider: identifier
ai_model: exact version
prompt_template_version: identifier
request_digest: hash
policy_version: identifier
```

Bundles are evaluated and applied atomically against a complete candidate forecast. This permits deterministic cross-variable validation: a bundle cannot accept a temperature change while rejecting the coupled dew-point change if that would create an invalid state. Replacement operations are disallowed initially except where deterministic policy first translates them into explicit bounded deltas.

### 7.5 Policy decision

```yaml
decision: accepted | needs_review | rejected
proposal_bundle_id: UUID
clipped_adjustment_artifact_id: optional
rules_evaluated: [...]
violations: [...]
policy_version: adjustment-policy.v1
reviewer: optional identity
decided_at: UTC timestamp
```

### 7.6 Observation contract

Observation records require:

- Station or sensor identity
- Location and elevation valid at observation time
- Observed variable and vertical definition
- Event time
- Reporting/ingestion time
- Value and unit
- Quality-control state
- Provider revision
- Raw artifact reference

Keeping both event and ingestion time is essential for realistic replay.

## 8. Temporal semantics

Weather systems commonly fail through implicit time assumptions. MesoForge should define these semantics centrally.

- All stored instants use UTC.
- `forecast_reference_time` identifies the model cycle or forecast issuance basis.
- `lead_time` is a duration from reference time.
- `valid_time` is derived and validated, not independently trusted.
- Instantaneous fields and interval fields are distinct.
- Accumulations always include `interval_start`, `interval_end`, and interval closure convention.
- PoP always identifies its valid interval and probability definition.
- QPF transformations must preserve accumulation windows and document differencing.
- Observation event time and ingestion time are separate.
- Forecast issuance time and publication time are separate.
- Daylight-saving and local calendar concepts belong only in presentation and configured local-day products.
- A run records an `information_cutoff`; no input first available after that cutoff may participate in a replayed forecast.

Interpolation policies must be variable-specific. Linear time interpolation may be acceptable for temperature, while accumulated precipitation requires interval-aware redistribution or must remain unaligned.

## 9. Spatial semantics

A versioned grid registry should define:

- Coordinate reference system
- Projection parameters
- Grid shape and resolution
- Coordinate bounds or cell centers
- Domain geometry
- Longitude convention
- Grid orientation
- Land/sea and terrain metadata versions

Every spatial transformation records:

- Source and destination grid IDs
- Method and library version
- Weight artifact ID
- Extrapolation behavior
- Coverage mask
- Conservation expectations

Recommended defaults:

- Bilinear interpolation for smooth scalar fields where appropriate
- Nearest-neighbor for categorical fields
- Vector-aware treatment for wind
- Conservative remapping for accumulated quantities where scientifically justified
- Explicit point-extraction rules including station elevation handling

Regridding weights should be cached as immutable artifacts keyed by source grid, target grid, method, and software version.

## 10. Provenance and reproducibility

A forecast run should be modeled as an immutable directed acyclic graph of artifacts and activities. Provenance should answer:

- What inputs contributed?
- Which source bytes were used?
- What did each transformation do?
- Which code and dependency environment ran it?
- Which configuration and policy versions were active?
- Were any data missing or substituted?
- Was AI involved?
- What was proposed, rejected, clipped, or accepted?
- Who approved publication?

Reproducibility levels should be stated explicitly:

1. **Logical reproducibility:** same inputs and versions produce scientifically equivalent output.
2. **Artifact reproducibility:** the exact historical output is retained and retrievable.
3. **Bitwise reproducibility:** pursued only where valuable and feasible.

For every operational run, retain:

- Git commit
- Container or environment digest
- Lockfile digest
- Configuration snapshot
- Source inventory and checksums
- Random seeds
- Numerical library versions
- AI provider/model identifier and request/response digests
- All intermediate artifact identities needed for replay

Because external AI models may change or disappear, exact AI replay cannot be assumed. Preserve the complete structured request and response, subject to privacy and licensing rules, and treat the original AI response as an immutable input to downstream replay.

## 11. Deterministic baseline design

The first baseline should be intentionally understandable and consist of two immutable stages:

1. Select eligible guidance by variable, horizon, coverage, freshness, and quality.
2. Transform it onto a common temporal and spatial frame.
3. Apply a variable-specific blend operator and an explicitly approved contributor set to emit an `UncorrectedBlendForecast`.
4. Apply deterministic corrections from one eligible frozen bias snapshot to emit the final `BaselineForecast`.
5. Enforce variable-domain and cross-variable constraints at both stages.
6. Emit contribution and correction breakdowns linking both artifacts.

The forecasting domain owns application of a bias estimate; the bias domain owns training, snapshot eligibility, and production of that estimate. A correction is applied exactly once, between the uncorrected blend and final baseline. Verification retains both artifacts as counterfactuals.

Example blend configuration:

```yaml
variable: air_temperature_2m
lead_band: PT0H/PT18H
contributors:
  HRRR: 0.50
  NBM: 0.30
  GFS: 0.20
approved_availability_sets:
  - available: [HRRR, NBM, GFS]
    weights: {HRRR: 0.50, NBM: 0.30, GFS: 0.20}
  - available: [HRRR, NBM]
    weights: {HRRR: 0.60, NBM: 0.40}
fallback_priority: [NBM]
minimum_spatial_coverage: 0.99
unapproved_combination: fail_closed
```

Weights should initially be configuration, not hidden learned parameters. Never renormalize an arbitrary surviving contributor set. Each permitted availability combination has reviewed weights, required cell/time coverage, and a quality state; fallback output is marked degraded and publication policy decides whether it is publishable. Later optimization can propose weights, but promotion should produce a new versioned baseline configuration.

The contribution record should make each baseline value explainable as source contribution plus deterministic correction.

There is no generic numeric blender. The variable registry binds each canonical variable to a blend operator, missingness policy, bounds, and contribution schema. Scalar weighted means may serve temperature/dew point; wind blends vector components before deriving speed/direction; PoP uses a probability/calibration-aware rule; QPF preserves accumulation windows and nonnegativity; precipitation type uses a categorical or probability-vector rule with temperature, PoP, and QPF consistency checks; gusts use a dedicated bounded operator rather than the sustained-wind rule.

## 12. AI adjustment safety model

### 12.1 AI input scope

Do not send raw national grids to a general-purpose model. Supply compact, structured evidence such as:

- Baseline values and trends
- Model spread and outliers
- Run-to-run changes
- Local climatological and learned bias summaries
- Diagnostics
- Observation recency summaries
- Known data-quality issues
- Explicit adjustment limits

AI output must conform to a strict schema. Free-form text may accompany a proposal but cannot control computation.

### 12.2 Deterministic guardrails

Policy should enforce at least:

- Variable allowlist
- Geographic and forecast-horizon scope
- Per-variable maximum absolute adjustment
- Maximum temporal step change
- Maximum spatial gradient introduced
- Wind-vector and speed limits
- PoP range of 0–100%
- Nonnegative QPF
- Configured PoP–QPF consistency
- Temperature and dew-point consistency when both are present
- Missing-data prohibitions
- Evidence completeness
- AI confidence threshold
- Model-spread-aware bounds
- Rejection of malformed or unsupported operations

Bounds should vary by lead time, geography, season, regime, and evidence quality only through versioned deterministic policy.

Policy validates and applies the entire proposal bundle atomically to a copy of the full baseline forecast. It then re-runs all single-variable and cross-variable invariants. Partial bundle acceptance is forbidden in v1; the policy rejects the bundle or returns a complete clipped bundle for human review.

### 12.3 Control modes

Support explicit operating modes:

- `disabled`: baseline only
- `shadow`: proposals recorded but never applied
- `review_required`: eligible proposals require human approval
- `limited_auto`: only low-risk proposals may be accepted automatically

Begin in shadow mode, advance to review-required, and introduce limited automation only after retrospective and prospective evidence.

### 12.4 Fail-safe behavior

If the AI provider, validator, or policy engine fails, publish the deterministic baseline if it otherwise passes quality checks. AI availability must never be required to issue a forecast.

Maintain global, domain, variable, and model-specific kill switches.

## 13. Bias learning without leakage

Bias learning is especially vulnerable to accidental use of future information.

### 13.1 Training example definition

Each example should represent what was knowable at a historical decision time:

```text
features = data available by historical information_cutoff
target   = quality-controlled observation for the forecast valid time
```

A feature is eligible only if its recorded ingestion time is no later than the cutoff. This applies to guidance revisions, observations, diagnostics, and prior verification aggregates.

### 13.2 Dataset construction

Use an append-only observation history with revisions rather than overwriting observations. Dataset builders should accept:

- Training cutoff
- Forecast issue-time range
- Observation latency policy
- Source revision policy
- Geography and regime filters
- Feature-contract version
- Label-contract version

The resulting dataset receives a manifest and immutable ID.

### 13.3 Validation strategy

Random row splits are inappropriate. Prefer:

- Rolling-origin temporal validation
- Entire-event holdouts for major weather episodes
- Seasonal holdouts
- Spatial holdouts for claimed geographic generalization
- Final untouched evaluation periods

Near-duplicate forecast cycles from the same weather event must not straddle train and validation folds without deliberate justification.

### 13.4 Initial models

Begin with transparent estimators:

- Rolling mean bias by station, model, variable, lead band, and season
- Shrinkage toward regional/global bias under sparse data
- Robust estimators to reduce sensitivity to outliers
- Explicit sample counts, effective age, and uncertainty

More complex machine learning should be adopted only if it demonstrates stable out-of-time improvement. Every inference references a frozen model snapshot and declares applicability. Sparse or drifting regimes should cause abstention or shrinkage, not extrapolation.

### 13.5 Promotion

Bias model promotion should require:

- Reproducible training manifest
- Leakage audit
- Performance against the current baseline
- Performance by lead, location, season, and weather regime
- Tail-event and calibration analysis
- Operational cost estimate
- Approval record
- Rollback target

## 14. Verification and backtesting

### 14.1 Matching

Forecast-observation matching must be a versioned operation that defines:

- Temporal tolerance
- Spatial matching or interpolation
- Station elevation policy
- Accumulation-window equivalence
- Observation QC eligibility
- Handling of revisions and missing data

Store matched pairs as durable artifacts to make metric changes separable from matching changes.

### 14.2 Metrics

Initial metrics should include:

- Temperature: bias, MAE, RMSE
- Wind speed: bias, MAE, RMSE
- Wind direction: circular error metrics, conditioned on minimum speed
- PoP: Brier score, reliability, resolution, ROC/AUC where appropriate
- QPF: bias, MAE, RMSE, categorical threshold scores, equitable threat score where appropriate
- Ensemble guidance: spread-skill, rank histograms, CRPS where feasible

Report sample size and uncertainty. Aggregate scores must be stratified by lead time, geography, season, weather regime, source availability, and AI-adjustment status.

### 14.3 Forecast comparison

Every verification record should distinguish:

- Raw source guidance
- Deterministic baseline
- Bias-corrected baseline
- AI-recommended forecast
- Policy-clipped forecast
- Human-approved published forecast

This makes it possible to measure the incremental value and harm of every layer.

AI value claims require paired counterfactuals sharing the exact run, source availability, uncorrected blend, final baseline version, information cutoff, and verification match policy. Metrics report proposal coverage, abstentions, policy rejections, human rejections, and publishable opportunities as separate denominators. “AI-recommended forecast” means the numerically applied proposal bundle before policy clipping; it is never inferred from rationale text. Unpaired aggregate comparisons cannot be used for promotion.

### 14.4 Backtest engine

Backtests should invoke the same application services and scientific functions used operationally, with an as-of artifact resolver replacing live discovery.

A backtest specification should pin:

- Historical issue-time range
- Domain and variables
- Guidance availability simulation
- Configuration versions
- Bias snapshot strategy
- AI response strategy
- Observation revision policy
- Metrics and comparison variants

For AI experiments, support both replay of preserved historical responses and new-model experiments. These are different claims and must be labeled separately.

## 15. Orchestration

Use a workflow orchestrator appropriate for Python data workflows—Prefect or Dagster are pragmatic candidates. Keep the scientific core independent of the chosen orchestrator.

Initial operational flow:

```text
discover cycle
  → acquire available assets
  → decode and normalize
  → validate source coverage
  → align guidance
  → compute source-native and aligned-comparative diagnostics
  → generate deterministic uncorrected blend
  → apply one eligible bias snapshot to create final baseline
  → compute baseline-derived diagnostics
  → request AI proposal
  → evaluate adjustment policy
  → optional human review
  → publish forecast
  → ingest observations asynchronously
  → match and verify after valid time
```

Required orchestration behavior:

- Idempotent tasks keyed by logical input identity
- Bounded retries for transient provider failures
- Clear terminal states for invalid data
- Partial-source deadlines
- Late-arriving model update policy
- Backfills isolated from operations
- Concurrency and memory controls
- Artifact-level caching
- Manual rerun with preserved parameters

The application database, not the orchestrator UI, should remain the authoritative source of forecast state and provenance.

## 16. Storage architecture

### 16.1 Object storage

Use S3-compatible object storage for:

- Raw GRIB files
- Zarr or NetCDF canonical arrays
- Regridding weights
- Forecast grids
- Diagnostic grids
- Training datasets
- Backtest outputs
- Rendered products

Zarr is a strong default for chunked cloud-accessible arrays, but the project should benchmark Zarr against compact NetCDF for its actual access patterns. Chunking belongs in artifact metadata because it materially affects performance.

### 16.2 Relational metadata store

Use PostgreSQL for:

- Artifact manifests
- Forecast runs and state transitions
- Provenance relationships
- Configuration registrations
- Model and grid catalogs
- Adjustment proposals and decisions
- Human review records
- Publication records
- Experiment metadata

PostGIS may be added when spatial query needs justify it. Do not store large numeric grids in PostgreSQL.

### 16.3 Tabular analytical storage

Use partitioned Parquet for:

- Observations
- Matched forecast-observation pairs
- Verification metrics
- Training features and labels
- Operational event exports

DuckDB is suitable for local analysis and early backtests. A distributed warehouse should be introduced only when demonstrated volume or concurrency requires it.

### 16.4 Cache

Begin with local or object-store-backed caches. Add Redis only when distributed locking, short-lived shared state, or high-volume request caching becomes necessary.

### 16.5 Retention tiers

Define separate retention for:

- Raw source bytes
- Normalized guidance
- Intermediate diagnostics
- Published forecasts
- Provenance and audit records
- Observations
- Backtest artifacts

Published forecasts, decisions, and audit metadata should have the strongest retention. Regenerable intermediates can use shorter lifecycle policies after reproducibility has been demonstrated.

## 17. API and UI boundaries

### 17.1 API

Use FastAPI for the initial application API. Separate command and query concerns logically, while keeping one deployable application.

Representative resources:

```text
GET  /models/cycles
GET  /forecast-runs/{id}
```

### 17.2 UI

The UI should consume only supported application APIs and purpose-built read models. It should not query workflow-engine internals or object storage directly.

Initial views:

- Model-cycle and ingestion health
- Forecast run status
- Baseline and adjusted forecast comparison
- Source contributions and model spread
- AI recommendation with cited evidence
- Policy violations and clipping
- Human approval workflow
- Forecast lineage
- Verification dashboards
- Backtest comparison

A map-centric UI may use a modern web framework and a geospatial renderer, but frontend selection can remain open until the first product slice defines visualization needs.

- Viewer
- Forecaster/reviewer
- Publisher
- Scientist/experimenter

## 21. Testing strategy

### 21.1 Unit tests

Cover:

- Unit and coordinate transformations
- Accumulation-window logic
- Blend and fallback rules
- Diagnostic formulas
- Policy limits
- Verification metrics
- Event-time eligibility

### 21.2 Contract tests

Validate every supported model adapter against pinned small fixtures:

- Expected coordinates and variables
- Unit conversions
- Lead and valid times
- Accumulation semantics
- Missing-field behavior
- Schema compatibility

Fixtures committed to Git are synthetic or minimal decoded-message samples. Any larger GRIB fixture is external, checksum-pinned, fetched on demand, and covered by documented provider licensing/retention terms.

### 21.3 Scientific regression tests

Maintain compact “golden case” datasets for known weather situations. Compare outputs with tolerances and require explicit approval for scientific changes.

Cases should include:

- Ordinary conditions
- Frontal passage
- Convective precipitation
- Snow or mixed precipitation
- High-wind event
- Model outage or delayed cycle
- Domain edge and missing coverage
- Daylight-saving transition in presentation products

### 21.4 Property-based tests

Useful invariants include:

- `valid_time = reference_time + lead_time`
- PoP remains within bounds
- QPF remains nonnegative
- Blend weights sum correctly after fallback
- Wind component conversion round-trips within tolerance
- Accepted adjustments never exceed policy
- No backtest feature has availability after its cutoff

### 21.5 Integration tests

Run a small end-to-end cycle from a pinned raw artifact through publication and verification using local object storage and a temporary database.

### 21.6 Operational tests

Test:

- Idempotent reruns
- Partial downloads
- Late model arrival
- AI timeout
- Invalid AI output
- Database or object-store interruption
- Baseline fallback
- Kill switches
- Backfill isolation

### 21.7 Performance tests

Benchmark representative xarray operations, chunk layouts, regridding, and point extraction before broad deployment. Scientific array performance is sensitive to chunking and should not be inferred from toy datasets alone.

## 22. Deployment evolution

### Stage 1: Local development

- One Python environment
- Local filesystem or MinIO
- PostgreSQL in containers
- In-process API and worker
- DuckDB for analysis
- Manual or local workflow execution

### Stage 2: Single production environment

- Containerized API and workers
- Managed PostgreSQL
- S3-compatible object storage
- Workflow scheduler
- Separate worker queues or pools for download, CPU-heavy, and memory-heavy jobs
- Central logs, metrics, traces, and secrets
- Static UI deployment

This remains one codebase and one logical application.

### Stage 3: Horizontal workers

Scale only demonstrated bottlenecks:

- Acquisition workers
- Decode/regrid workers
- Backtest workers
- AI request workers
- Product-rendering workers

Use artifact references and durable task messages. Avoid transferring large arrays through a message broker.

### Stage 4: Selective service extraction

Extract a module only when it has a clear reason, such as:

- Independent scaling profile
- Distinct availability requirement
- Security boundary
- Separate ownership
- Technology constraint
- Excessive deploy coupling demonstrated in practice

Likely candidates are bulk array processing, observation ingestion, and backtest execution. Forecast policy and provenance should remain closely governed even if execution becomes distributed.

## 24. Major tradeoffs

### Modular monolith versus microservices

**Recommendation:** modular monolith.

Advantages include rapid iteration, fewer deployments, straightforward local development, and easier consistency across scientific and audit records. The cost is the need for disciplined import boundaries and workload isolation. Versioned contracts and artifact-based task seams mitigate later extraction cost.

### Zarr versus NetCDF

Zarr supports chunked parallel and cloud-native access; NetCDF is mature and portable. Use source GRIB as the immutable raw layer, benchmark normalized formats, and permit artifact-type-specific choices instead of imposing one format universally.

### Prefect versus Dagster

Both are credible. Dagster emphasizes data assets and lineage; Prefect often offers a lighter task-flow experience. Select through a short spike using cycle ingestion, partial availability, backfill, and artifact registration. Do not let orchestrator-native metadata replace MesoForge provenance.

### Configuration versus learned blends

Begin with versioned configured weights for explainability. Learned blends can improve performance but introduce training, leakage, drift, and interpretability risks. Treat learned weights as governed model artifacts.

### Grid-first versus station-first forecasts

Grid-first better supports maps and broad domains but is more computationally expensive. Station-first accelerates local verification and product value. The recommended first vertical slice is station or small-domain focused while retaining contracts that support grids.

### AI model type

A language model can synthesize structured evidence and generate explanations, but numeric or spatiotemporal correction models may eventually be better for field adjustments. Keep “recommendation” abstract enough to host both, while subjecting all outputs to the same deterministic policy.

## 25. Principal risks and mitigations

| Risk | Consequence | Mitigation |
|---|---|---|
| Source formats or availability change | Failed or silently incorrect ingestion | Adapter contracts, source manifests, canary checks, pinned fixtures |
| Temporal accumulation errors | Material QPF/PoP defects | Interval-aware types, dedicated tests, reject ambiguous inputs |
| Regridding distorts fields | Scientific error | Method registry, cached weights, conservation and regression tests |
| Hidden provenance gaps | Forecast cannot be explained | Mandatory artifact manifests and lineage before publication |
| AI produces plausible but unsafe advice | Forecast degradation | Structured proposals, hard bounds, shadow mode, abstention, kill switches |
| Verification leakage | Inflated expected performance | As-of joins, ingestion timestamps, temporal/event holdouts |
| Observation quality or revisions | Incorrect labels and metrics | Revision-aware storage, QC flags, matching-policy versions |
| Model outages | Missed forecasts | Deadlines, partial-source policy, deterministic fallback |
| Array workloads exhaust memory | Operational instability | Chunk benchmarks, bounded workers, artifact materialization |
| Metric optimization harms extremes | Unsafe tail behavior | Regime and threshold stratification, event holdouts |
| Configuration proliferation | Unclear operational state | Schemas, immutable snapshots, promotion workflow |
| Premature platform complexity | Slow delivery | Modular monolith, managed infrastructure, evidence-driven extraction |
| External AI model changes | Non-repeatable behavior | Exact identifiers, response preservation, provider abstraction |
| RRFS/product evolution | Contract instability | Isolated adapter and explicit experimental/operational status |

## 27. Recommended initial decisions

Unless product requirements dictate otherwise:

- Use Python 3.12 or the newest version supported reliably by the scientific stack.
- Use xarray, Herbie, Dask where beneficial, NumPy, pandas, Pint/pint-xarray, and pyproj.
- Use Pydantic for control-plane contracts.
- Use PostgreSQL for metadata and S3-compatible object storage for artifacts.
- Use Parquet and DuckDB for early analytical workloads.
- Use FastAPI for application APIs.
- Evaluate Prefect and Dagster with a narrow operational spike.
- Use immutable configuration snapshots validated from YAML.
- Begin with HRRR temperature and wind over one small domain.
- Build observation matching and verification before AI integration.
- Begin bias learning with robust rolling estimators and shrinkage.
- Keep AI entirely in shadow mode until baseline and backtest credibility are established.
- Require human review for the first operational AI-adjusted forecasts.
- Treat auditability and baseline fallback as release-blocking requirements.

## 28. Architectural acceptance criteria

The initial architecture is successfully realized when MesoForge can demonstrate that:

1. A forecast value can be traced to exact source artifacts and transformations.
2. The same historical run can be replayed under pinned inputs and configuration.
3. Time intervals, accumulations, grid definitions, and units are unambiguous.
4. Baseline output is deterministic and available without AI.
5. Every AI proposal is structured, bounded, policy-evaluated, and auditable.
6. AI failure cannot prevent a valid baseline forecast.
7. Verification distinguishes baseline, proposed, accepted, and published values.
8. Backtests enforce historical information cutoffs.
9. Bias models are frozen, versioned, evaluated out of time, and reversible.
10. Domain modules can be tested independently without running the API or orchestrator.
11. Large data move through artifact storage rather than APIs or task messages.
12. Operational health includes data-quality and forecast-quality signals.
13. New models can be added through adapters without rewriting the forecast core.
14. Scaling can occur through workers before any service extraction is required.
15. Every canonical variable/slice can be traced to exact GRIB messages and decode parameters.
16. Uncorrected blend, deterministic correction, and final baseline are distinct artifacts and correction is applied once.
17. Unsupported contributor combinations fail closed rather than being silently renormalized.
18. Multi-variable adjustments are policy-checked and applied atomically.
19. Dew point, wind gust, and precipitation type are either implemented through their named Phase 2 contracts or explicitly disabled from publication.

This structure gives MesoForge a scientifically defensible core, a safe boundary around AI assistance, and a practical route from a small forecasting experiment to a reliable operational platform.
